## 一、技术架构类

### Q0. 新增的官网落地页是怎么做的？未登录 / 登录怎么分流？

**一句话结论**：`/` 根路径用 Next.js 服务端组件判断登录态——未登录展示营销落地页，登录后重定向到产品主界面 `/market`。

**展开**：
- 新增 `app/(marketing)/` 路由组：`page.tsx`（服务端组件，`getCurrentUserId()` 判登录态 → 已登录 `redirect("/market")`）、`layout.tsx`、`landing.css`（官网专属样式）。
- 落地页 `components/marketing/LandingPage.tsx`：Hero（主标题 + 注册/逛市场 CTA + 对话窗口预览）+「能做什么 / 如何开始 / 内容类型」三个模块（`ShowcaseStage.tsx` 卡片）+ CTA + 页脚。
- 登录/注册/退出后统一跳 `/market`（`lib/login-redirect.ts` 默认 `next=/market`）；侧边栏 Logo 链接按登录态切换 `/market` 或 `/`。
- 价值：把「营销转化」和「产品使用」解耦——未登录访客先看产品价值，登录用户直达工作台。

### Q1. 为什么选 Next.js 全栈，而不是前后端分离（Vue/React + Java/Node）？

**一句话结论**：单人项目要「快」，Next.js App Router 一个仓库同时搞定 SSR 页面和 API 路由，减少协作和部署成本。

**展开**：
- 项目用 **Next.js 16（App Router）+ React 19 + TypeScript strict**，页面在 `app/(main)/**`，接口在 `app/api/**`，天然同构。
- 好处：类型共享、鉴权逻辑复用（`getCurrentUserId()` 服务端组件直接读 Cookie）、`middleware.ts` 统一拦截 API、部署只需一个 Node 进程 + Docker 镜像。
- 代价：AI 流式长连接、文件导出等 CPU 密集操作和页面渲染在同一进程，后续量大可把 AI/导出拆成独立服务——这在我的「未来规划」里。

### Q2. 为什么用 SQLite 而不是 MySQL/PostgreSQL？扛得住并发吗？

**一句话结论**：MVP 阶段单人/小团队，SQLite 最轻量、零运维；代码里已为 PostgreSQL 迁移留好后路。

**展开**：
- 用 **SQLite + WAL 模式**（`PRAGMA journal_mode=WAL`），读写不互斥、支持并发读。
- 针对 SQLite 的并发瓶颈，我做了三层缓解（技术文档 5.10）：
  1. 高频读接口走 **Redis 缓存**（推荐流 TTL 5 分钟，写后失效）；
  2. 表结构变更用**幂等迁移**（`CREATE TABLE IF NOT EXISTS` + `addColumnIfMissing`），不靠手改；
  3. 预留了 `scripts/migrate-to-postgres.ts` 迁移脚本，数据量上来（数据库 > 2GB）就切 PostgreSQL。
- SQL 全用参数化查询，且刻意避免 SQLite 特有语法，方便日后平滑迁移。

### Q3. AI 对话具体怎么实现的？为什么选 SSE 而不是 WebSocket？

**一句话结论**：后端把大模型输出转成 SSE 事件流推给前端，SSE 实现成本低、走 HTTP 天然穿透代理，够用。

**展开**：
- 接口 `POST /api/chat/sessions/:id/generate` 返回 `text/event-stream`。
- 事件协议（技术文档 5.8.1）：`data: {"type":"content","content":"...","seq":1}`、`data: {"type":"heartbeat","ts":...}`、`data: {"type":"done","message_id":"..."}`，还扩展了 `conflict`（冲突检测）、`affinity`（好感度）事件。
- 细节：每 **15s 心跳**保活、**180s 总超时**、前端 `AbortController` + 后端内存标志实现「**停止生成**」。
- 选 SSE 而非 WebSocket：对话是**单向流式**场景，SSE 用普通 HTTP，部署反代（Nginx）无需额外配置，浏览器 `fetch` 流式读取即可，复杂度远低于 WS。

### Q4. 如何接入多个大模型？失败怎么降级？

**一句话结论**：抽象成 OpenAI 兼容协议统一接口，再做「主模型 → 备模型」降级链。

**展开**：
- `lib/ai-provider.ts` 把所有 provider 统一到 `/chat/completions` 流式接口；`lib/model-manager.ts` 管理用户自建模型（DeepSeek/OpenAI/Anthropic/Ollama/自定义，各做 Base URL 归一化，如 DeepSeek 自动补 `/v1`）。
- 用户可在「设置 → AI 模型管理」增删模型、设默认模型，**会话级**也能切换模型（`chat_sessions.model_id`）。
- 降级：`getFallbackModelIds()` 把主模型排前面、其余已启用模型做备选，主模型失败且**尚无输出**时自动切下一个，全失败才回退到占位输出，保证永远有东西返回。

### Q5. RAG 是怎么做的？没有向量数据库也能检索吗？

**一句话结论**：知识库词条先做 embedding 存 SQLite，用余弦相似度召回；没有 embedding 时退化到关键词匹配，两套都可用。

**展开**：
- `lib/rag-engine.ts`：世界知识库词条写入 `rag_vectors` 表，有 `OPENAI_API_KEY` 时用 `text-embedding-3-small` 生成向量，检索时算**余弦相似度**取 Top N（默认 3 条）。
- 关键兜底：**没有向量库/没有 Key 时，自动退回关键词分词匹配**（中文按 bi-gram 切分），保证任何环境都能检索。
- 注入位置：`lib/prompt-context.ts` 里把召回片段作为「参考资料」塞进 system 层，并明确要求「不要杜撰与设定冲突的内容」，从而缓解长篇一致性问题。

### Q6. 推荐算法具体怎么算的？

**一句话结论**：`0.45×点赞 + 0.25×作者热度 + 0.20×标签匹配 + 0.10×新鲜度`，登录用户再加个性化。

**展开**：
- `lib/recommendation-engine.ts`：点赞分做归一化、作者热度看粉丝数、标签匹配用用户点赞过的标签画像、新鲜度做 30 天半衰期时间衰减。
- 落地分两路：非登录用户直接用 SQL 里等价的 `recommended` 排序表达式；登录用户取 100 条候选后用 `buildUserProfile()` + `sortByRecommendationScore()` 个性化重排取 30 条。
- 曝光/点击日志（`feed_impressions`/`feed_clicks`）也已埋点，为后续优化留数据。

---

### Q7. 大模型上下文有限，写长篇小说怎么保证一致性？

**一句话结论**：分层 Prompt + 历史截断 + RAG 召回 + 一致性校验，四管齐下。

**展开**：
- 上下文只注入**最近 12 条**历史消息，控制 token；
- 世界观/角色/文风作为 system 层「硬设定」常驻，不随历史被截掉；
- 世界知识库走 RAG 按需召回，避免把整个世界设定全塞进去；
- 另有 `lib/consistency-checker.ts` 对角色身份、时间线、地点做规则校验，命中矛盾给「自动修正 / 保持原文」二选一；
- 文风保持器 `lib/style-anchor.ts` 抽取高频词/句长/情感强度等特征，只注入摘要向量，不回灌全文。

## 二、安全类

### Q8. 登录鉴权怎么做？JWT 安全吗？

**一句话结论**：密码 scrypt 哈希存储，登录签发 JWT 放 HttpOnly Cookie，7 天过期。

**展开**：
- 密码用 **scrypt（N=16384, r=8, p=1）+ 16 字节盐**，格式 `scrypt$N$r$p$salt$hash`，验证用 `timingSafeEqual` 防时序攻击。
- JWT 用 `jose` 库、HS256 算法，`sf_session` Cookie 标记 HttpOnly，前端 JS 无法读取，降低 XSS 窃取风险。
- 密钥从 `JWT_SECRET` 环境变量读取，长度 < 16 直接拒绝服务，避免弱密钥。

---

### Q9. 如何防止 CSRF / 越权 / 重放？

**一句话结论**：middleware 校验 Origin/Host + 敏感接口防重放 nonce + 资源级鉴权。

**展开**：
- `middleware.ts` 拦截所有 `/api/*` 写请求，做**跨站变更防护**（`isCrossSiteMutationBlocked` 校验 Origin/Referer，防 CSRF）。
- 发布/注销等敏感接口要求 `x-timestamp + x-nonce`，`lib/anti-replay.ts` 校验 5 分钟时窗内 nonce 不重复（`used_nonces` 表）。
- 越权：所有写接口先 `getCurrentUserId()` 拿身份，再校验「资源归属」，作者只能操作自己的故事/角色/世界，管理员走单独的管理员列表鉴权。

---

### Q10. 内容安全（涉黄涉政）怎么处理？

**一句话结论**：输入输出双向过滤 + Prompt 系统层合规约束 + 人工审核兜底。

**展开**：
- 系统 Prompt 首条就是「禁止涉政/涉黄/涉暴、禁止 OOC」硬约束，从源头约束模型；
- `lib/content-filter.ts` 对用户输入、发布文本做敏感词片段扫描和长度限制，发布前必检；
- 生成后还跑**冲突检测**，把违规/矛盾内容以 `conflict` 事件追加到流里提示；
- 兜底有 `/admin/moderation` 审核台（`moderation_items` 表），管理员可「通过 / 下架 / 驳回并备注」，全部处理写入 `basic_logs` 审计。

---

### Q11. 用户敏感信息怎么保护？

**一句话结论**：手机号只存脱敏值，账户注销走合规流程。

**展开**：
- 手机号只存 `phone_masked`（如 `138****1234`），校验 `^1[3-9]\d{9}$`，完整号码不落库；
- 头像上传限制 `JPG/PNG`、单文件 ≤ 5MB，用 sharp 生成 200×200 缩略图；
- 注销走 `lib/account-deletion.ts`：二次确认（输入「确认注销」）→ 状态置 `deleted` → 会话失效 → 作品可选「匿名保留（作者显示『已注销用户』）」或「下架删除」→ 清空点赞/关注/通知。

## 三、产品与业务类

### Q12. 这个项目和 SillyTavern 有什么区别？为什么要做？

**一句话结论**：SillyTavern 是极客向的「角色扮演聊天引擎」，StoryForge 把它「产品化」成面向大众的「AI 写书工具」。

**展开**：
- SillyTavern 强在模型接入和卡牌生态，但门槛高、无出版闭环；StoryForge 保留了「酒馆式对话」的核心体验，补上了**章节大纲、人物关系图、导出电子书、市场发布、互动推荐**这一整套从「聊」到「书」到「发布」的闭环。
- 定位：让不写代码的人也能「和 AI 聊出一本小说」。

---

### Q13. 你的核心创新点 / 亮点是什么？

**一句话结论**：把 AI 对话生成「结构化」，并围绕它做了一整套创作辅助与内容闭环。

**展开**（挑 3 个讲）：
1. **分层 Prompt + RAG 检索**：系统/世界/角色/文风/资料/历史 六层上下文组装，兼顾一致性和 token 成本；
2. **多模型降级链 + SSE 流式**：任意 OpenAI 兼容模型即插即用，失败自动切换，体验不断流；
3. **创作辅助三件套**：冲突检测（P0/P1/P2 分级）、一致性校验、文风保持器，直击「AI 写长篇会崩人设」的痛点；
4. **完整闭环**：创作 → 生成 → 导出 EPUB/PDF → 发布市场 → 被体验/点赞/关注/通知。

---

### Q14. 好感度、人设面具、二创分别是什么？

- **好感度**（`affinity_scores` 表）：用户和角色互动时，系统根据互动内容估算情感增量（`estimateAffinityDelta`），动态调整 AI 语气的亲密度，角色会话有 0~100 的进度条。
- **人设面具**（`persona_masks` 表）：用户自定义「自己在故事里扮演谁」，进入故事体验时选中，AI 就把「用户」当作这个身份，而不是路人甲。
- **二创**（`derivative_relations` 表 + `work_downloads` 表）：用户可以把市场作品「下载到本地」再二次创作，系统记录 `inspired_by / remix / continuation` 衍生关系，展示二创关系链。

## 四、工程与部署类

### Q15. 部署架构？storyforge.fun 是怎么上线的？

**一句话结论**：Docker 多阶段构建 + Nginx 反向代理 + 域名，一条 `docker-compose up` 起服务。

**展开**：
- `Dockerfile` 三段式：`deps`（安装编译 sqlite3 原生依赖）→ `builder`（`npm run build` 产出 standalone）→ `runner`（node:22-slim + 非 root 用户运行，`output: standalone`）。
- `docker-compose.yml` 暴露 3000 端口、挂载 `storage` 数据卷、带 `healthcheck`（每 30s 探活）、`restart: unless-stopped`。
- 服务器上 Nginx 把 80/443 反代到容器，域名 storyforge.fun 解析过去（仓库有 `scripts/apply-domain-nginx.sh`）。
- 数据持久化在 `storage/` 卷（SQLite 库 + 用户文件 + 导出物），容器重建数据不丢。

---

### Q16. 数据库怎么备份和恢复？

**一句话结论**：WAL 模式 + 每日备份脚本 + 保留策略。

**展开**：
- 仓库有 `scripts/backup.ts`（`npm run backup`）和 `scripts/restore.ts`（`npm run restore`）；
- 备份文件命名 `db_backup_YYYYMMDD.sqlite`，放 `storage/backups/db/`，保留最近 7 天；
- 恢复流程：停写 → 选备份覆盖 → 回放当日增量（如有 WAL）。

---

### Q17. SQLite 单文件，多个请求同时写会不会冲突？

**一句话结论**：WAL + 单写者 + 写请求短事务，MVP 量级足够。

**展开**：
- WAL 模式下「读写不互斥」，只有「写写」互斥；SQLite 本身是单写者模型；
- 我的写操作都是**短事务**（单条 INSERT/UPDATE），持锁时间极短；
- 读多写少的场景（市场、推荐）用 Redis 缓存扛住读压力；
- 真要高并发写，迁移方案已经写好（PostgreSQL），这是明确的演进路径。

## 五、项目复盘类

### Q18. 开发中遇到的最大难点 / 踩过什么坑？

**一句话结论**：AI 流式长连接 + 原生依赖部署，是踩坑最多的两块。

**展开**（挑讲）：
1. **SSE 长连接的稳定性**：模型慢时要保活（心跳 15s）、要能中止（AbortController + 内存停止标志）、要防无限挂起（180s 总超时），这些都是在真实环境反复调试出来的；
2. **sqlite3 原生模块的 Docker 部署**：不同 base 镜像 glibc 不一致会导致 `sqlite3` 加载失败，最后让「编译」和「运行」用同一发行版（node:22-bookworm），并 `npm rebuild sqlite3 --build-from-source` 解决；
3. **国内服务器访问外网 AI/Google**：用 undici 全局代理（`instrumentation.ts` 启动时 `setGlobalDispatcher`）统一走代理。

---

### Q19. 如果继续做，下一步会做什么？

**一句话结论**：先 PostgreSQL + Redis 规模化，再做多模型/社区生态。

**展开**（对应技术文档里程碑）：
1. **存储升级**：SQLite → PostgreSQL（双写灰度迁移），Redis 全面接管缓存/限流；
2. **AI 增强**：多模型实时切换、RAG 向量库（如 pgvector）、更长的上下文管理（摘要压缩 + 关键设定置顶）；
3. **社区生态**：评论体系、二创关系链可视化、活动广场；
4. **商业化**：计费/会员/配额系统。

---

### Q20. 这个项目有什么不足 / 你自己怎么评价？

**一句话结论**：诚实地讲——「内容安全是轻量级、一致性是启发式、单机存储有上限」。

**展开**（主动暴露短板显真实，再补「但我有预案」）：
- 内容过滤目前是「敏感词片段 + 模型约束」的 MVP 级，还做不到完整审核工单体系——已有 `/admin/moderation` 人工兜底；
- 一致性校验是**规则为主 + AI 为辅**的启发式，无法 100% 保证长篇逻辑完美——这是当前大模型的通用难题，我的思路是「检测 + 提示 + 人工二选一」；
- 单机 SQLite + 进程内限流，多实例部署时需 Redis 化——代码里 `cache.ts`/`rate-limit.ts` 已预留接口，迁移脚本就绪。

## 附：回答问题的通用技巧

1. **先给结论，再展开**：评委问得多，一句话抓住重点，再补细节。
2. **往代码/文档上引**：说「这个在 `lib/xxx.ts` 里」「技术文档 5.8.5 有写」，显得是真做过。
3. **主动暴露短板 + 给预案**：比硬吹更可信。
4. **不会的别硬编**：可以说「这块我 MVP 阶段简化了，但我预留了演进方案 X」。
